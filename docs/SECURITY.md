# セキュリティ

この文書は、E.L.V.A.R. が何を守り、何を守れないかを、正直に書いたものです。
設計の細部は `docs/ELVAR_MULTIUSER.md`（§2〜§4）にあります。

## 守りたいもの

1. 利用者の**データ**（人格、ノート、会話、ファイル）を、ほかの利用者から。
2. 利用者の**秘密**（AIのAPIキー、Google・MCPのトークン）を、データベースの漏れから。
3. 運営者のインフラ（Supabase、Vercel）を、利用者の悪用から。

## 利用者どうしの分離（テナント分離）

- すべてのユーザーデータは、非公開スキーマ `app` の表に入ります。全行に `user_id` があります。
- すべての表で、行レベルセキュリティ（RLS）を有効にして**強制**（force）します。`anon` と `public` に権限はありません。表は、`app._secure()` を通して作る決まりです。
- ブラウザは、表に直接さわれません。Data API（PostgREST）に `app` を出しません。すべての読み書きは、サーバーを通ります。サーバーが、容量・上限・承認を確かめます。
- サーバーは、専用ロール `elvar_app` で接続します。リクエストごとのトランザクションで、検証済みのユーザーIDを `request.jwt.claims` に入れ、`set local role authenticated` にしてから、SQLを打ちます。切り替えたあとに、`current_user` と `auth.uid()` を読み戻して照合します。合わなければ中止します。設定を忘れたときは、0行になります（失敗は閉じます）。
- アクセストークン（JWT）は、サーバーが Supabase の公開鍵（JWKS）で検証します。ES256 か RS256 だけを受け付けます。発行元、対象、期限、`role`、匿名でないことも確かめます。
- 子テーブルは、`(user_id, parent_id)` の複合キーで親につなぎます。他人の親の行には、ぶら下げられません。
- Storage は、非公開のバケットです。本人の `users/<uid>/` の下だけを読めます。書き込みには、生きているアップロード予約が必要です。上書きはできません。
- 管理者用のRLSポリシーはありません。管理画面は、返す列を固定した関数（メール、日付、状態、容量、回数）だけを使います。
- Android の通知同期だけは、用途を限った端末トークンを使います。そのトークンで読める範囲は、通知の送受信だけです。
- テストが確かめること: 全テーブルが RLS 強制・`user_id`・`on delete cascade`・データ台帳に載っていること。2人のユーザーで、すべての表とすべてのAPIの経路を、他人のIDで叩いて断られること。（`npm test` と `npm run test:db`）

## 秘密の暗号化（封筒暗号）

- ユーザーごとに、32バイトのランダムな鍵（DEK）を作ります。
- DEK は、運営者の鍵（`ELVAR_KEK`）で、AES-256-GCM で包んで保存します。KEK は、Vercel の環境変数にあり、データベースの外です。
- APIキーとOAuthトークンは、DEK で AES-256-GCM で暗号化します。認証付きの追加データ（AAD）に、ユーザーIDと名前を入れます。行を別の人や別の名前にすり替えても、復号に失敗します。
- 承認チケット（書き込みの承認）の署名鍵も、DEK から導きます。
- アカウントを削除すると、鍵を捨てます（crypto-shred）。バックアップに残った暗号文も、読めなくなります。
- KEK の回転ができます（`ELVAR_KEK_PREV`）。

## 誰に何が見えるか

| 誰 | APIキー・トークン | ノート・会話・ファイル | 容量・回数など |
|---|---|---|---|
| 本人 | 書き込みだけ。「設定済み・末尾4桁」だけ表示 | 見る・直す・書き出す・消す | 見える |
| ほかの利用者 | 不可 | 不可 | 不可 |
| アプリ内の管理者 | 不可 | 不可 | 見える（メール、日付、状態、容量、回数） |
| データベースだけを手に入れた人 | 不可（KEK がない） | **平文で読める** | 読める |
| **運営者**（Vercel と Supabase の両方の画面を持つ人） | **技術的には可** | **可** | 可 |

### 正直な限界

- **ノートと会話は、保存時に列単位では暗号化していません**（Supabase の保存時の暗号化だけです）。全文検索を使えるようにするための決定です（決定 O4）。そのため、Vercel と Supabase の両方のダッシュボードを持つ運営者は、ノートと会話を平文で読めます。データベースだけが漏れた場合も、ノートと会話は読まれます。
- **秘密は、データベースだけでは読めません。** KEK が別の場所にあるからです。ただし、サーバーがLive会話の開始やGoogleの更新のために秘密を使う以上、Vercel の環境変数（KEK）とデータベースの両方を持つ人は、秘密も読めます。
- **`ELVAR_DB_URL` は、全ユーザーの行を読める資格情報と同じです。** `elvar_app` は、任意のユーザーIDを名乗れます。RLSが防ぐのは、サーバーのバグと、盗まれた利用者のトークンです。接続文字列の漏れは、防げません。Sensitive の環境変数に入れて、漏れたらパスワードを替えます。
- **`SUPABASE_SECRET_KEY`（service role）は、強い権限です。** 使う場所を、Auth の管理操作とStorageの掃除などに限っています（`server/db/service.js` だけが読む。テストで確かめます）。
- **KEK をなくすと、全員の秘密が読めなくなります。** 控えは、運営者の責任です。
- AIの内容は、利用者が選んだAIサービス（Gemini など）に送られます。そこから先は、そのサービスの規約に従います。ファイルの中身をAIに渡すときは、承認カードが出ます。
- 運営者は、バックアップなどの運用について、利用者に説明してください。

## そのほかの対策

- **Gemini Live**: 音声は、ブラウザから Google に直接つながります。サーバーは、利用者本人のキーで、短命・1回限り・設定固定のトークンを発行します。
- **書き込みの承認**: Googleや連携アプリの書き込みは、署名付きの許可証（引数のハッシュ、2分、1回限り）が要ります。承認カードの「承認して実行」だけが、それを送ります。メールやファイルの中の命令に従わないよう、人格にも指示してあります。
- **連携アプリのネットワーク**: https だけ。解決したアドレスに固定して接続します。社内・ループバック・リンクローカル・予約済みの範囲は断ります。共通プラットフォームでは、プライベートネットワークへは常に不可です（`ELVAR_ALLOW_PRIVATE_CONNECTORS` は、1人で動かす場合のスイッチです。共通プラットフォームでは使わないでください）。
- **OAuth**: PKCE と、1回限りの `state`。途中の情報は暗号化して、本人の行に置きます。他人の `state` を知っていても、横取りできません。
- **ブラウザ**: Cookie を使いません。JSON以外の書き込みは 415 で断ります。CSP などのヘッダーは `vercel.json` にあります。
- **サインアップ**: メール確認、Turnstile（任意）、使い捨てメールの拒否、1日の上限、ネットワークごとの上限（Auth Hook）。Hook は、ホスティングされた Supabase では**手で有効にする必要があります**（`docs/SETUP.md` §1.7）。
- **レート制限と上限**: 1分あたりのリクエスト数は、インスタンスごとの数え方です（厳密なメーターではありません）。毎日・毎時の上限は、データベースの数字です。
- **削除**: 外部のトークンを失効、Storage の全バケット、鍵の破棄、認証ユーザーの削除、残りの確認、の順です。

## 脆弱性の報告

脆弱性を見つけたら、**公開の Issue には書かないでください。**

1. このリポジトリの GitHub の「Security」タブで、「Report a vulnerability」（非公開の脆弱性報告）を使ってください。
2. そのボタンが無いときは、公開の Issue で「非公開で連絡できる方法を教えてください」とだけ書いてください。脆弱性の内容は書かないでください。

報告には、次のことを書いてください。

- 何が起きるか（影響）。
- 再現の手順。
- 確かめた版（コミット）。

できるだけ早く返事をするよう努めます。修正が出るまで、公開しないでください。

運営者へ: 自分のプラットフォームを公開するときは、利用者が連絡できる窓口（メールなど）を、プライバシーポリシーに書いてください。
